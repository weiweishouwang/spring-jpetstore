## 1. 测量方法

| 项目 | 内容 |
| --- | --- |
| 工具 | `scripts/load-profile.py`（标准库实现，固定样本、可重复） |
| 指标 | 延迟分位数（p50/p90/p95/p99/max/mean）、吞吐（请求/秒）、错误率、并发度 |
| 请求类型 | 默认只发只读请求；写请求必须显式授权（`--allow-writes`），只允许指向已确认的测试环境 |
| 目标约束 | 工具默认只接受本机目标；其他目标会被拒绝，未知目标一律不执行 |
| 并发上限 | 1～32，默认 2；超限直接拒绝执行 |
| 服务端指标 | `jpetstore.orders{outcome="placed|failed|stock-conflict|replay|lock-failure"}`（低基数，只有 outcome 标签） |

命令形态：

```bash
python3 scripts/load-profile.py \
  --target http://127.0.0.1:8080 \
  --request "GET /api/categories" \
  --request "GET /api/items/EST-1" \
  --iterations 50 --concurrency 4
```

## 3. 资源限制与观察

| 项目 | 观察 |
| --- | --- |
| 连接池 | 测试与开发环境为 4/1（`backend/pom.xml` 的 failsafe 配置）；生产用 Hikari 默认值，由部署参数覆盖 |
| 事务边界 | 下单在单个事务内完成：幂等占位 → 快照锁 → 购物车锁 → 升序扣库存 → 写订单 → 消费快照与购物车 |
| 锁顺序 | 库存按 itemid 升序加锁，减少死锁；死锁与锁等待超时映射为 `ORDER_RETRYABLE`（503） |
| 热点 | 单 SKU 的并发下单会串行在同一库存行上，表现为 p99 抬升而不是错误率上升 |
| 幂等 | 同键重试不新建订单，重放路径的延迟显著低于首次下单路径 |

## 4. 瓶颈与已知限制

1. **库存行是串行点**：同一 SKU 的并发下单会排队，吞吐上限由数据库的行锁决定；这是有意为之的
   正确性代价（Q02 禁止超卖）。
2. **幂等键唯一索引是另一个串行点**：同键重试会等待前一次尝试提交（plan §5.7 的设计）。
3. **本报告不设 SLO**：实测数值只用于观察与回归对比，不作为容量承诺。
